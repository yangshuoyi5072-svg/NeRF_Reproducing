# NeRF Apple Silicon (MPS) 适配开发总结报告

本项目旨在将原始 NeRF (2020) 的 PyTorch 实现适配至搭载 Apple Silicon (M1/M2/M3) 芯片的 Mac 环境，并利用 MPS (Metal Performance Shaders) 进行硬件加速。以下是开发过程中遇到的挑战、原因分析及解决方案。

## 1. 设备调用与张量一致性问题

### 问题描述
初始运行脚本时出现 `RuntimeError: Expected all tensors to be on the same device`。代码在尝试进行射线计算或模型前向传播时，提示部分张量在 `cpu` 上，而模型在 `mps:0` 上。

### 原因分析
*   **硬编码设备**：原代码库多处硬编码了 `cuda` 或 `cpu`，未考虑 `mps` 后端。
*   **隐式 CPU 张量创建**：PyTorch 的许多工厂函数（如 `torch.linspace`, `torch.meshgrid`, `torch.ones`）在不指定 `device` 时默认创建 CPU 张量。在 NeRF 这种包含大量中继计算（如射线生成 `get_rays`）的算法中，手动一个个修改非常容易遗漏。

### 解决方案
*   **优先 MPS 检测**：修改设备选择逻辑，优先级排序为 `mps` > `cuda` > `cpu`。
*   **全局默认设备（关键）**：在脚本初始化阶段增加 `torch.set_default_device('mps')`。这确保了所有中间生成的、未显式指定设备的张量都会自动分配到 GPU 上，彻底消除了设备不匹配的隐患。

---

## 2. 训练画面“全白”与位置编码损坏（核心挑战）

### 问题描述
适配后训练能够运行，但在 Iter 10000 渲染出的视频画面为空（仅有背景色渐变），且 Loss 无法降至合理区间。经诊断，模型输出的密度（Density/Alpha）始终接近 0，意味着射线没有击中任何几何体。

### 原因分析
*   **Lambda 闭包捕获 Bug**：NeRF 使用 `Embedder` 类生成位置编码，其中通过 Lambda 函数捕获频率参数 `freq`。
*   **0D CPU Tensor 兼容性**：捕获的 `freq` 是一个从 CPU Tensor 迭代出来的 0 维张量。在 MPS 后端下，Lambda 内部通过该 0D 变量进行的标量乘法运算（`x * freq`）发生了**静默计算错误**，导致位置编码输出完全损坏，模型无法从错误的坐标信息中学习到任何三维结构。

### 解决方案
*   **原生类型强制转换**：在构建 Lambda 列表前，将频率张量通过 `.tolist()` 转换为 Python 原生浮点数列表。确保 Lambda 捕获的是数值而非 Tensor 对象，从而规避了 MPS 标量广播计算的底层 Bug。

---

## 3. MPS 内存布局与算子稳定性

### 问题描述
在分层采样（Hierarchical Sampling）阶段，代码偶尔表现不稳定或出现计算偏差。

### 原因分析
*   **非连续内存敏感度**：PyTorch 的 MPS 后端对非连续（non-contiguous）张量的支持尚不及 CUDA 成熟。代码中通过 `.expand()` 创建的视图在某些特定算子（如 `torch.gather`）中处理时，如果内存布局不连续，可能会返回错误结果或报错。

### 解决方案
*   **显式 Contiguous 化**：在 `sample_pdf` 函数调用 `torch.gather` 之前，强制执行 `.contiguous()`。这保证了底层金属框架（Metal）在读取张量数据时处于连续状态，提高了分层采样的数值稳定性。

---

## 验证结果
经过上述三项核心修复，Lego 场景在 500 步测试训练中表现如下：
*   **收敛速度**：PSNR 从 8.0dB 快速攀升至 **14.2dB**，Loss 降至 **0.08**（修复前 Iter 5000 仍在 0.28 左右震荡）。
*   **渲染输出**：首帧渲染统计确认 `Acc`（不透明度）峰值达到 **1.0**，完美捕捉到了推土机的几何轮廓，不再是之前的空白渐变。

## 结论
在 Mac 环境下跑 NeRF，最关键的不是简单的设备切换，而是要警惕 **隐式 CPU 张量带来的混合计算失效** 以及 **MPS 对 Lambda 闭包中 Tensor 捕获的兼容性陷阱**。通过全局设备设置和输入数据的原生化处理，可以获得非常接近 CUDA 的训练稳定性。



怎么把 Apple 空间视频拆解成我们需要的数据，以及为什么要做“插值”来处理深度图。

1. 我们的数据是怎么获取的？
Apple Vision Pro 或 iPhone 15 Pro 拍摄的“空间视频”并不是单纯的 mp4，它实际上内部同时打包了高分辨率的彩色影像、相机运动轨迹，以及记录三维距离的深度数据。在这个开源数据集中，作者已经提取好了所有的这些原始素材供我们拼装：

彩色图像 (RGB images)：我们用 cv2 去读取打包在 videos/ 文件夹里的 .mp4 视频文件。根据打标好的时间戳索引 indexes.txt，从中间抽出了 18 张最关键的无动态、高视差连贯帧，作为 NeRF 的主要渲染目标，将它们输出成了正经的 frame_000x.png。
空间深度数据 (Depths)：真实的深度信息被藏在一个 .zip 里的 .exr 半浮点格式文件中。我们用 OpenEXR 库去读取它记录下的倒数深度（Inverse Depth），然后通过 1.0 / (inv_depth) 这个公式将它还原成了实实在在的物理距离（米）。
相机位姿与参数：每张照片你不仅需要知道“拍了什么”，还要知道“相机在什么坐标”。我们读取了原始数据集给定的 poses.npy（相机 3D 旋转位移）、intrinsics.npy（相机的焦距）。接着在这个基础上，将普通的 OpenCV 坐标系翻转适配到 NeRF/Blender 使用的三维坐标系，并结算成 JSON 文件。
2. 深度插值是什么意思？为什么必须做这一步？
这个问题要归结于硬件底层的限制： 摄像头的彩色传感器像素非常高，所以录制下来的 RGB 视频分辨率足有 1280x720，非常清晰。但用来记录真实距离的 LiDAR 雷达或是深度神经引擎受算力及功耗限制，它的“视网膜”分辨率其实非常低，原生深度图只有 584x328 的马赛克大小！

这就产生了一个严重的数据错位：

RGB 图片宽度是 1280 个像素；
Depth 深度矩阵宽度只有 584 个像素。
如果在 NeRF 训练时不插值会怎样： NeRF 的核心逻辑是：“我向屏幕的 第 [700, 1100] 这个高分辨率像素坐标发射一条光线，我要用它对应的真实深度来监督它！”。但由于你的深度图到了 584 就断层了，系统找不到第 1100 个像素对应的深度，代码就会立刻报错崩溃 IndexError。

"插值" (Interpolation) 就是解决这个问题的桥梁： 我们在生成的预处理脚本里使用了 cv2.resize(...)。当我要把一个 584x328 大小的低分辨率深度矩阵强行拉伸（放大）到精确的 1280x720 时，中间会突然多出几十万个空缺的空白像素。插值算法（Bilinear Interpolation 双线性插值） 就会通过周围已知像素的深度值，平滑推理出这个新生空白像素最有可能的物理深度，从而自动脑补填满这些断层。

这样一来，你的彩色图片和深度矩阵就像两片完美的吐司，大小边角 100% 精准对齐（都是 1280x720），重合覆盖在彼此身上。NeRF 在追踪任何一条高清光线时，都能查到完美配对对应的物理深度了！

多模态对齐（Multimodal Alignment） 的核心难点：精度与分辨率的权衡。

我们先快速复盘一下数据获取的“前世今生”，再重点攻克你关于“插值不准”的疑虑。

1. 数据获取的底层逻辑

这个过程就像是在进行一场“数字考古”，把 iPhone 录制的压缩包拆解成 3D 模型能懂的语言：

彩色影像 (RGB)：从 3D 空间视频（Side-by-Side 格式）中提取。我们只取左半边（左眼），并缩放到 1280×720。

物理深度 (Depth)：这是最硬核的部分。iPhone 的 LiDAR 或双目视觉生成的深度图存储在 .exr 文件里。

原始数值：它是 Inverse Depth（逆深度，1/d）。

物理还原：通过 Depth=1.0/(Value+1e−6) 变成米。

位姿 (Poses)：数据来自 iPhone 的 IMU 和 ARKit 视觉里程计。脚本的作用是把它们从 Apple 的坐标系“翻译”成 NeRF 能读懂的矩阵。

2. 什么是“深度插值”？（为什么 584 必须变 1280）

由于硬件物理限制，iPhone 的深度感应器（LiDAR）分辨率远低于彩色镜头。

RGB 图像：1280×720（清晰，细节丰富）。

原生深度：584×328（模糊，像马赛克）。

插值（Interpolation） 的意思就是：当我们要把 584×328 的小矩阵拉伸到 1280×720 时，对于那些“多出来”的像素点，我们根据周围已有点的深度值，用数学公式（如双线性插值）计算出一个“最有可能”的值来填满空隙。

3. 你的核心疑虑：插值不准了，NeRF 训练怎么办？

这是一个非常棒的学术问题。既然插值是“猜”出来的，那 Loss 不就错了吗？这里有三个维度的解释来消除你的顾虑：

A. 几何连续性假设 (Geometric Continuity)

在现实世界中，除了物体的边缘（Edge），绝大多数表面（墙面、桌面、地板）都是连续平滑的。
对于平滑表面，插值算出来的深度值与真实值几乎没有物理偏差。只有在物体边缘那 1-2 个像素的地方，插值会产生轻微的“毛刺”或“模糊”。但相对于整个场景几十万个像素来说，这种误差在统计学上是可以被 NeRF 忽略的。

B. NeRF 的“平滑器”作用

NeRF 本质上是一个神经网络（MLP），它具有天然的 低通滤波（Low-pass filter） 特性。
即使你的深度图在插值时引入了一些微小的噪声，神经网络在训练过程中会自动“磨平”这些不自然的抖动。它学习的是整体的 3D 结构，而不是死记硬背某一个像素点的深度。

C. 为什么不降低 RGB 的分辨率去对齐深度？

你可能会想：那我把 1280 的 RGB 缩小到 584 不就对齐了吗？

代价巨大：如果你这样做，你会损失掉大量的纹理细节（比如墙上的字、物体的边缘）。

NeRF 的需求：NeRF 极其依赖高质量的 RGB 信息来计算光度一致性（Photometric Consistency）。宁可要一个“经过插值、稍有误差”的高清深度图，也不要一个“准确但模糊、细节全无”的低清 RGB 图像。

🛠️ 工业界的“标准做法”是什么？

为了解决你担心的“不准”问题，我们在代码中通常采取以下策略：

插值算法选择：
我们不使用普通的线性插值，而是使用 cv2.INTER_NEAREST（最近邻插值） 或 双线性插值。

最近邻：保证深度值绝对来自原始观测，不会产生不存在的中间值，但会有锯齿。

双线性：更平滑，适合 DS-NeRF 这种需要连续梯度的情况。
